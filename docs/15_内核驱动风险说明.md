# 内核驱动风险说明（阶段 3）

> 一句话结论：**这个驱动是本工具里风险最高的部分**。它的价值只有"读到 PCIe 配置空间"这一件事，
> 但引入的代价包括 驱动签名、系统稳定性、反作弊误判、蓝屏回滚。所以它默认关闭，只在诊断机上按需加载。

## 一、风险清单

| # | 风险 | 具体表现 | 等级 | 缓解措施 |
|---|---|---|---|---|
| 1 | **加载行为被反作弊观测** | EAC/BE/Vanguard/ACE 都会监控内核驱动加载（`PsSetLoadImageNotifyRoutine`、驱动对象枚举、服务创建）。加载时机落在游戏运行期间，最坏结果是被会话内踢出或被标记 | 高 | 只在游戏未运行时加载；文档写死"先扫描、后启动游戏" |
| 2 | **驱动未签名 / 测试签名** | Secure Boot + HVCI 环境下，未签名驱动直接加载失败（错误 577 `ERROR_INVALID_IMAGE_HASH`）；开 testsigning 又等于改系统安全配置 | 高 | 正式使用必须 EV 证书 + Microsoft attestation 签名；测试仅限隔离 VM |
| 3 | **驱动被拉黑** | 反作弊厂商维护驱动黑名单（哈希/签名主体），一旦进入黑名单，装了这个驱动的机器可能连游戏都进不去 | 中高 | 不公开分发、不复用同一个二进制给多人，按客户单独签发 |
| 4 | **系统稳定性** | 内核代码任何空指针/越界都是 BSOD。配置空间读取失败路径、设备拔插竞态都是常见崩溃源 | 中 | 代码里所有缓冲区长度校验、IRP 同步等待、失败即返回错误不重试 |
| 5 | **对设备的副作用** | 读配置空间是只读操作，但错误的 IRP 参数（Offset/Length 越界）可能让某些总线驱动异常 | 中 | 限制 Offset=0、Length≤256 且 4 字节对齐；只发 `IRP_MN_READ_CONFIG`，绝不发 `WRITE_CONFIG` |
| 6 | **提权面** | 任何能打开 `\\.\PcieCfg` 的进程都能读配置空间。若设备对象 ACL 过宽，低权限进程也能用 | 中 | IOCTL 内做 Token 提权检查（`SeQueryInformationToken`），非管理员直接拒绝 |
| 7 | **服务残留** | 异常退出导致服务没删掉，下次开机残留（虽然是 DEMAND_START 不会自启） | 低 | `finally` 强制 stop+delete；启动时先清理同名旧服务 |
| 8 | **合规/审计风险** | 企业环境里加载自制内核驱动需要变更审批 | 中 | 只在授权诊断场景使用，保留加载/卸载审计日志 |

## 二、使用约束（硬性）

1. **默认不加载**。不加 `--kernel` 参数，工具完全不知道驱动存在。
2. **不在反作弊活跃期加载**。启动游戏前完成扫描；游戏运行中不加载、不保留驱动。
3. **用完即卸**。`CreateService → StartService → IOCTL → ControlService(STOP) → DeleteService`，全程 `try/finally`，不留服务、不留句柄。
4. **不设自启动**。`StartType = SERVICE_DEMAND_START`，INF 与代码双重保证。
5. **不随包分发**。`PcieCfg.sys` 不进默认发布包，谁要用谁单独签名编译。
6. **只在授权机器上跑**。客户机诊断需事先告知并取得同意。

## 三、与反作弊的共存判断

| 场景 | 是否允许加载 | 说明 |
|---|---|---|
| 游戏未启动、反作弊服务未运行 | ✅ 允许 | 推荐姿势：开机后先扫，再开游戏 |
| 反作弊服务已运行、游戏未进对局 | ⚠️ 谨慎 | 部分反作弊在服务启动时就枚举驱动，此时加载会被记录 |
| 游戏运行中 | ❌ 禁止 | 最容易被判定为可疑行为 |
| Vanguard 开启（含开机自启 vgk） | ❌ 禁止 | Vanguard 常驻监控驱动加载，且 Secure Boot 下自签驱动装不上 |

## 四、失败模式与回滚

| 失败点 | 现象 | 回滚动作 |
|---|---|---|
| `StartService` 返回 577 | 签名不被信任 | 停止使用，用户态结果照常输出，报告标 `kernel.loaded=false` |
| `StartService` 返回 1275 / 1058 | 驱动被策略阻止 / 服务被禁用 | 同上 |
| 打开设备失败 | 设备对象没创建（加载失败或已被占用） | 同 上 |
| IOCTL 超时 | 某个设备栈卡住 | 单设备超时跳过，继续下一个；整体扫描结束必卸载 |
| 扫描中途进程被杀 | 服务可能残留 | 下次启动时检测同名服务并先删除 |

## 五、为什么 BAR 大小拿不到（需求与安全约束的冲突点）

需求 1 要求输出"BAR 大小"。确定 BAR 大小的标准做法是**写配置空间**：先写 `0xFFFFFFFF`，读回掩码，再写回原值。这是**写操作**，与"只允许读取"的硬性限制直接冲突，且写错会让设备掉线。

本实现的取舍：

- 驱动只读 BAR 寄存器原值，解析出 **类型（IO / 内存）、位宽（32/64 位）、是否预取**；
- 结果里显式带 `barSizeDeterminable = false` 和 `configSpaceAvailable` 说明；
- BAR 大小的近似值仍由用户态资源报告（阶段 2 的 WMI `Win32_PnPAllocatedResource`）提供。

这不是偷懒，是刻意不做的动作：任何写配置空间的代码都不进这个驱动。
