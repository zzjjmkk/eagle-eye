# AI 视觉外挂检测 — 设计（阶段 5，设计稿，未编码）

> 定位：**线索收集器**，不是判定器。
> 结论上限：本机用户态最高只能给出「可疑」，且必须标注"需游戏侧遥测确认"。

---

## 1. 与现有架构的集成方式

### 1.1 不新增独立子系统，复用现有三层

```
ScanOrchestrator（现有）
├─ ProcessScanner   现有：进程/路径/模块/签名
├─ FileScanner      现有：只读遍历 + SHA256
├─ DmaScanner       现有：SetupAPI 枚举 + 可选一次性内核配置空间
└─ VisionScanner    新增：只组合上面三者已经产出的数据，几乎不引入新采集面
   ├─ CaptureLayer      进程 + 窗口 + 句柄 三类线索
   ├─ RuntimeLayer      模块名/文件名的弱信号
   ├─ ParasiticLayer    OBS 寄生模块 + 插件文件哈希
   ├─ HardwareLayer     复用 DmaScanner 的 RawDevice 列表，只换规则集
   └─ BehaviorLayer     可选，GetCursorPos 轮询的统计摘要
```

关键设计：**VisionScanner 不重复枚举**。它消费 ProcessScanner 已经拿到的 `ProcessRecord`（含模块列表、签名、路径），只在需要时补两类新查询：窗口枚举、句柄枚举。

### 1.2 数据结构

```csharp
public sealed class VisionIndicator
{
    public string Id;                 // 规则 id
    public string Layer;              // capture | runtime | parasitic | hardware | behavior
    public string Category;           // overlay | capture_hook | inference_runtime | video_capture | hid_injector | input_mapper | motion_stat
    public string Target;             // 进程名 / 设备名
    public int? Pid;
    public string? Path;
    public int Severity;              // 1-3 为主，视觉线索不应给 4-5
    public double Confidence;         // 0-1，普遍 <=0.6
    public string Description;
    public string? Advice;            // "需游戏侧遥测确认"等
    public Dictionary<string,object?> Evidence;
    public bool NeedsTelemetry = true;// 恒为 true，强制提醒
}
```

### 1.3 报告字段

```jsonc
"visionCheatIndicators": {
  "note": "双机+外部采集+硬件注入链路在本机用户态无法独立确证，以下为可观测线索，不代表最终判定。",
  "software": [ VisionIndicator ],   // 采集端 / 推理运行时 / 寄生模块
  "hardware": [ VisionIndicator ],   // 采集卡 / HID 模拟器 / 输入映射器
  "behavior": [ VisionIndicator ],   // 输入统计摘要（信息级）
  "layerSummary": {
    "capture": 2, "runtime": 1, "parasitic": 0, "hardware": 1, "behavior": 0
  },
  "independentLayers": 2,
  "highestLevel": "可疑",
  "levelCapped": true
}
```

### 1.4 聚合规则（与主引擎分离）

```
单层命中          → 信息（无论置信度多高）
≥2 个独立层命中   → 可疑（上限）
任何情况          → 不超过「可疑」，永远不进入主 risk_score
```

理由写进代码注释：视觉线索的误报面太大（OBS 主播、录屏、辅助功能、双屏用户），不能与进程/内存类证据同权。

### 1.5 CLI

```
--vision                启用视觉外挂线索扫描（默认只跑模块/窗口，便宜）
--vision-handles        追加句柄枚举（贵，需管理员，1-3s）
--vision-behavior       追加输入统计（默认关，信息级）
--vision-only           只跑视觉模块自检
```

## 2. 每类线索的数据来源（具体 API / 枚举路径）

### 2.1 CaptureLayer — 软件采集端

| 线索 | 数据来源 | 说明 |
|---|---|---|
| 谁持有游戏进程的高权限句柄 | `NtQuerySystemInformation(SystemExtendedHandleInformation=64)` → 过滤 `ObjectTypeIndex == Process` → `OpenProcess(PROCESS_DUP_HANDLE)` → `DuplicateHandle` → `GetProcessId` 比对游戏 PID → 记录 `GrantedAccess` | 只看 `VM_READ(0x10)` / `VM_WRITE(0x20)` / `CREATE_THREAD(0x2)` 这类高权限；`SYNCHRONIZE`、`QUERY_LIMITED` 属正常，不报 |
| 叠加层窗口（overlay） | `EnumWindows` → `GetWindowLongPtr(GWL_EXSTYLE)` 取 `WS_EX_LAYERED/TOPMOST/TRANSPARENT` → `GetWindowRect` 与游戏窗口矩形比对 → `GetWindowThreadProcessId` 回溯进程 | 纯用户态；overlay 是最常见的 ESP/AI 框显示方式 |
| 候选进程的 GDI/USER 资源量 | `GetGuiResources(hProcess, GR_GDIOBJECTS / GR_USEROBJECTS)`（`PROCESS_QUERY_LIMITED_INFORMATION`） | 持续高频截图会显著抬高 GDI 对象；只作辅助权重 |
| 采集相关模块 | 复用 ProcessScanner 已枚举的模块列表，匹配 `dxgi/d3d11/d3d12/nvfbc/dwmapi/Windows.Graphics.Capture` 等 | 绝大多数正常程序都加载 dxgi → 只作为权重，不单独成条 |
| 屏幕拓扑异常 | `EnumDisplayDevices` / `GetSystemMetrics(SM_CMONITORS)` | 游戏在全屏 + 存在"无显示输出的虚拟显示器/采集卡输出"→ 弱信号 |

**明确不做**：不给目标进程注入 DLL 去 hook `BitBlt`/`IDXGIOutputDuplication::AcquireNextFrame`；不读进程内存找 hook 痕迹。

### 2.2 RuntimeLayer — 推理运行时弱信号

| 线索 | 数据来源 |
|---|---|
| 已加载推理/CV 模块 | 复用 ProcessScanner 的 `MODULEENTRY32W.szModule`：`onnxruntime*.dll`、`tensorrt*.dll`、`nvinfer*.dll`、`cudnn*.dll`、`opencv_world*.dll`、`opencv_dnn*.dll`、`libtorch*.dll`、`torch_cpu.dll`、`directml.dll`、`openvino*.dll`、`Microsoft.AI.MachineLearning.dll` |
| 模块签名状态 | 现有 `SignatureChecker`（Authenticode + 目录签名） |
| 模块路径异常 | 模块路径在 `%TEMP%` / `Downloads` / 非 Program Files |
| 模型文件存在 | FileScanner 扩展 `includeExtensions`：`.onnx .engine .trt .pt .pth .plan .safetensors`；只做**名称与哈希**比对 |

**明确不做**：不读进程内存判断模型内容、不解析 ONNX/engine 文件、不做 API 调用计数。

> 注意：装了 CUDA 的游戏本、跑 Stable Diffusion 的用户都会命中 → severity 只能给 1-2，confidence ≤ 0.3。

### 2.3 ParasiticLayer — OBS 寄生

| 线索 | 数据来源 |
|---|---|
| 游戏进程加载了采集 hook 模块 | 进程模块列表匹配 `graphics-hook64.dll` / `graphics-hook32.dll`（OBS Game Capture 注入的模块） |
| OBS 进程及其插件目录 | `%APPDATA%\obs-studio\plugins\`、`%ProgramData%\obs-studio\`、`<OBS 安装目录>\obs-plugins\64bit\` 下的 `.dll` |
| 已知寄生插件哈希 | FileScanner 对上述目录做 SHA256，比对规则库 `vision.parasitic.hashRules` |
| OBS 来源异常 | `obs64.exe` 的签名主体非 "OBS Project"/"OBS Studio"，或路径不在 Program Files → 改造版 |

**不做**：不判断插件是否"用于作弊"（无法从文件层面区分直播与作弊）。

### 2.4 HardwareLayer — 设备枚举（复用现有框架）

直接吃 `DmaScanner` 的 `RawDevice`（VID/PID/设备类/服务名/位置），只换规则集，**不新增任何采集代码、不新增内核组件**。

| 类别 | 识别依据 |
|---|---|
| `video_capture` | 设备类 `Camera`/`Image`；服务 `usbvideo`；VID 命中采集卡厂商（Elgato `0x0FD9`、AVerMedia `0x07CA`、Magewell `0x2935`、Blackmagic `0x1EDB`、Inogeni、Datapath 等） |
| `hid_injector` | 出现"USB 输入设备"但厂商 ID 属开发板/串口桥（Arduino `0x2341`、Teensy `0x16C0`、CH340 `0x1A86`、CP210x `0x10C4`、RP2040 `0x2E8A`）+ 该设备在 `HIDClass` 下枚举 |
| `input_mapper` | 虚拟 HID 驱动服务名：`ViGEmBus`、`HidHide`、`Interception`、`reWASD`、`DS4Windows` 相关服务；设备名含 `Virtual Gamepad` |
| `dma_memory` | 复用阶段 2/3 已有的 FPGA VID/PID 与配置空间异常规则 |

输出时 `category` 字段分开标注，报告中按类别分组，**不合并成"一个可疑设备"**。

### 2.5 BehaviorLayer — 输入统计（可选、信息级）

| 指标 | 采集方式 | 说明 |
|---|---|---|
| 移动平滑度 | `GetCursorPos` 以 `sampleMs`(16ms) 轮询，计算相邻采样点向量夹角方差 | 只保留方差与分位值 |
| 直线化比例 | 连续 N 个采样点共线（夹角 < 阈值）的比例 | 机器瞄准常见"完美直线" |
| 匀速比例 | 速度标准差 / 均值 < 阈值 的连续段占比 | 人手有加减速，脚本常为匀速 |
| 微抖动缺失 | 采样位移的亚像素抖动为 0 的比例 | 软件模拟常见整像素跳变 |
| 空闲时间 | `GetLastInputInfo` | 仅辅助 |

**硬约束**：不装 `WH_MOUSE_LL` 钩子（那是 Hook）；不记录原始轨迹，采样在内存里滑动窗口计算后立即丢弃，只输出聚合值；不关联到具体窗口/游戏。

报告里固定标注：
> 行为统计为**信息级**，仅反映本机输入事件的宏观特征，正常玩家使用高 DPI 鼠标 + 平滑算法同样可能出现高分，**不可单独作为判定依据**。

## 4. 边界清单

### 4.1 本机用户态**可做**

- 哪些进程加载了推理运行时/OpenCV（模块名）
- 哪些进程在游戏之上挂了 layered+topmost 窗口（overlay）
- 哪些进程以 `VM_READ/VM_WRITE` 打开了游戏进程（句柄枚举，管理员）
- 游戏进程是否加载了 `graphics-hook64.dll`（OBS 采集 hook）
- 本机是否插入采集卡 / HID 开发板 / 虚拟手柄驱动
- 采集相关目录里是否存在已知哈希的寄生插件
- 输入事件的宏观统计特征（仅信息级）

### 4.2 本机**不可确证**

| 场景 | 为什么不可确证 |
|---|---|
| **双机链路**（PC-A 玩、PC-B 采集+识别+输出） | PC-B 上零痕迹；PC-A 只表现为"正常鼠标输入" |
| 采集卡接在另一台机器 | 本机 PnP 树里根本不存在该设备 |
| KMBox 类硬件输入注入 | 设备侧是标准 HID，主机无法区分"人手"与"硬件转发"，且不允许 hook 输入 |
| 模型内容 / 是否真的用于识别 | 不读进程内存、不解析模型文件 |
| 通用 UVC 摄像头 vs 采集卡 | 同一 VID/PID 也可能用于网课/直播 |
| OBS 合法录制 vs 外挂寄生 | 同一进程、同一模块，文件层面无差异 |
| 是否在对局中生效 | 需要游戏侧遥测（命中率异常、反应时间分布） |

### 4.3 结论口径

报告固定输出：

> 双机 + 外部采集 + 硬件注入链路在本机用户态无法独立确证，以下为可观测线索，不代表最终判定。
> 本地最高等级为「可疑」，最终认定需游戏侧遥测与人工复核。

禁止出现的措辞：`确认使用视觉外挂`、`检测到 AI 外挂`、`已确证`。

## 5. 与反作弊共存的风险评估

### 5.1 本模块新增的操作面

| 新增操作 | 权限 | 频次 | 可被反作弊观测 | 风险 |
|---|---|---|---|---|
| `NtQuerySystemInformation(SystemExtendedHandleInformation)` | 管理员 | 1 次/扫描 | 是（系统级调用，Process Explorer 同款） | 低 |
| `OpenProcess(PROCESS_DUP_HANDLE)` + `DuplicateHandle` | 管理员 | 每个候选进程 1-2 次 | 是（对方进程句柄表会多一个重复持有） | **中低** |
| `EnumWindows` / `GetWindowRect` / `GetWindowLongPtr` | 普通 | ~数百次 | 基本不可见 | 低 |
| `GetGuiResources` | `QUERY_LIMITED` | 1 次/候选进程 | 与现有进程枚举同级 | 低 |
| `GetCursorPos` 轮询 | 普通 | 625 次/10s | 不可见（无 Hook） | 低 |
| 设备枚举 | 普通 | 同阶段 2 | 同阶段 2 | 低 |
| 内核组件 | — | **0（不新增）** | — | 无 |

### 5.2 与各反作弊的共存判断

| 反作弊 | 风险点 | 缓解 |
|---|---|---|
| **EAC** | 句柄重复持有（DUP_HANDLE）在 EAC 监控范围内属常见行为，但若发生在游戏进程上会被记录 | 只对**非游戏、非反作弊**进程做 DUP_HANDLE；对游戏进程本身只做枚举不复制；跳过受保护进程 |
| **BattlEye** | BE 对"扫描类工具"敏感，尤其是枚举全系统句柄 | 默认 `--vision` 不跑句柄枚举；`--vision-handles` 需显式开启，并在报告中记录该操作 |
| **Vanguard** | Vanguard 会阻止对 `vgc/vgk` 的 `OpenProcess`（含 DUP_HANDLE）→ 调用失败 | 失败即跳过并记 `notChecked`；**绝不对 vgk/vgc 重试或提权**；Vanguard 环境建议只用默认模式 |
| **ACE / GameGuard** | 对窗口枚举/overlay 检测无感知 | 无特殊处理 |

### 5.3 性能与时机

- 句柄枚举在 200k 句柄量级机器上约 1-3s，CPU 瞬时占用明显 → **建议先扫描、后启动游戏**
- 行为统计会持续 10s 轮询 → 默认关闭，仅在有遥测比对需求时开启
- 与阶段 3 驱动一样：不在游戏运行期间执行重扫描

### 5.4 结论

本模块**不新增内核组件、不注入、不 Hook、不拦截输入**，新增操作全部属于用户态只读枚举，风险等级：**M0/M1 与反作弊共存无实质变化**；唯一需要谨慎的是 `--vision-handles` 的句柄复制，默认关闭、管理员限定、失败即跳过。
