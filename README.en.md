# Eagle Eye

[English](README.en.md) | [简体中文](README.md)

> **Author**: Tone Wang　·　**Contact**: 2802165750@qq.com

> A **read-only** local anti-cheat scanner for Windows x64. It looks for traces of cheating tools on this machine and writes a report with an evidence chain.

No DLL injection, no game memory reads, no API hooks, no screen capture, no network access.
Every result is a *lead with a confidence score*, never a verdict.

---

## What problem it solves

A player reports someone as a cheater, and you only have one machine. Eagle Eye sweeps every
**observable trace** on that machine — running processes, who opened the game process, loaded drivers,
injected modules, overlay windows, capture/HID devices — and ranks review priority by evidence strength.

For two-PC setups, external capture cards, or hardware input forwarding, the tool states plainly that
**nothing can be observed locally** instead of pretending the machine is clean.

## Quick start

1. Download `EagleEye-v1.0.0-win-x64.zip` from Releases and extract it
2. **Right-click → Run as administrator** (or open an elevated PowerShell) — protected game processes are unreadable otherwise
3. Either **double-click `EagleEye.exe`** (guided mode) or use the CLI:

```powershell
.\EagleEye.exe selftest      # 9 environment checks, all must pass
.\EagleEye.exe scan          # full scan
```

Results land in `out\reports\scan-<time>.json` and `.html` (double-click the HTML), logs in `out\logs\`.

More commands:

```powershell
.\EagleEye.exe scan --no-files                  # quick scan (skip file walking)
.\EagleEye.exe scan --profile deep              # deep scan (+byte signatures, +input stats)
.\EagleEye.exe validate                         # validate rule files only
.\EagleEye.exe aggregate --dir <reports> --tune # multi-machine rollup + auto tuning
```

> Tip: running with **no arguments** starts a guided wizard — it self-checks, offers elevation,
> runs the scan and opens the HTML report.

## Detection coverage

| Layer | What it checks | Needs samples | Strength |
|---|---|---|---|
| **Handles** | Who opened the game process with `VM_READ / VM_WRITE / CREATE_THREAD` | No | ★★★★★ |
| **Drivers** | Loaded kernel modules: blocklist + allowlist mode (any untrusted signer is reported) | No | ★★★★ |
| **Injection traces** | Modules in the game process that are missing on disk / in odd paths / unsigned | No | ★★★★ |
| **Process / module / signature** | Name, path, command line, loaded modules, Authenticode | No | ★★★ |
| **Overlay windows** | Layered + topmost + transparent windows covering the game (classic ESP) | No | ★★★ |
| **Vision chain** | Visible window × inference runtime / capture-hook modules | No | ★★★ |
| **DMA devices** | PCIe enumeration (VID/PID/class/service); optional one-shot read-only config-space driver | No | ★★★ |
| **Files** | Read-only traversal + SHA256 lists + byte signatures | Partial | ★★★ |
| **Game telemetry** | Pre-aim ratio, tracking jitter, reaction-time distribution (offline JSON import) | No | ★★★★★ |
| **Naming rules** | Heuristic process/file name patterns | No | ★ |

The top eight layers need **no malware samples** — a cheat must open the game process, load a driver and
inject a module. Those are structural traces; renaming the binary does not hide them.

## Risk model

```
score(rule) = severity(1-5) × 20 × confidence(0-1) × category weight
per-target sum capped at 100; a single strong signal (sev≥4 and ≥70) escalates directly;
three or more weak signals escalate together.
0-39 info / 40-69 suspicious / 70-100 highly suspicious
```

A whitelist hit **suppresses** the finding (no scoring) but keeps a record with the reason — fully auditable.

---

## Reports

- **JSON** — machine readable, full evidence for every finding
- **HTML** — single self-contained file, inline CSS, **zero external references**, opens offline
- **Audit log** (JSONL) — every process open with its access mask, signature checks, driver load/unload, no network

Anything that could not be checked is listed in `notChecked`: **not found ≠ clean**.

## Rules

External JSON; the whole `rules\` directory is loaded and merged by rule id, so updates need no rebuild.

```
rules\
├─ rules.json              core rules
├─ rules.delta-force.json  Delta Force specific (20 rules)
├─ rules.intel.json        name-based intel rules (75 rules)
└─ tuning.suggested.json   generated by the tuner (optional)
```

Helper scripts:

| Script | Purpose |
|---|---|
| `tools\hashgen.ps1` | sample folder → SHA256 rule pack |
| `tools\intel-to-rules.ps1` | keywords / web text → rules |
| `tools\tune-thresholds.ps1` | false-positive tuning (or `EagleEye.exe tune`) |
| `tools\collect-game-info.ps1` | capture game process baseline on site |
| `tools\audit-policy.ps1` | machine-checked red-line audit (18 checks) |
| `tools\package.ps1` | one-command packaging |

---

## Red lines (machine-checkable)

```powershell
powershell -File tools\audit-policy.ps1
```

All 18 checks must pass before release: no injection, no memory read/write, no hooks, no driver hiding,
no privilege escalation, no HVCI tampering, the driver only issues `IRP_MN_READ_CONFIG`, every rule has a
description, every finding carries evidence, and no network access.

The script strips comments before matching, so "never use `SetWindowsHookEx`" in a comment is not a false positive.

## Known limitations

- **Two-PC setups are invisible** — the second machine does the capture and inference; locally you only see normal mouse input
- **Hardware forwarding is invisible** — a KMBox-style device looks like a standard HID device
- **Kernel-hidden modules are invisible** — unlinked modules cannot be enumerated from user mode
- **Incomplete without admin rights** — protected processes are unreadable; the report marks `partialCoverage`
- **Naming rules are weak** — renaming the binary bypasses them; they are leads only
